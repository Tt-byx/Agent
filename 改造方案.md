## 1. 现状诊断

### 1.1 系统分层（改造前）

```
前端 Vue3 + Live2D  ──HTTP/WS──▶  Java 网关(Spring Boot)  ──HTTP──▶  Python(FastAPI)
                                        │                                  │
                                      MySQL                    ChromaDB / LLM API
                                                               ASR / TTS / 数字人驱动
```

### 1.2 关键事实（读码结论）

- **AI 能力全在 Python**：`backend-python/app/services/` 下有 `rag_service`、`embedding_service`、`vector_store`、`llm_service`（流式）、`asr_service`、`tts_service`、`digital_human/`。
- **Java 是空壳网关**：`ChatServiceImpl` 只做「转发 + 落库 + 本地情感分析」，`pom.xml` 里没有任何 AI 框架依赖。
- **RAG 是单轮的**：`rag_service.build_rag_prompt()` 只拼 `system` + 当前问题，历史对话完全不进上下文；上下文用 `MAX_CONTEXT_CHARS = 1500` 硬截断。
- **Agent 六项能力对照**：

| 能力          | 现状                                       | 评级 |
| ----------- | ---------------------------------------- | -- |
| 多轮记忆        | 完全没有，每轮独立                                | 缺  |
| 工具调用        | 完全没有                                     | 缺  |
| Agent 循环    | 单轮一问一答                                   | 缺  |
| 上下文管理       | 仅 1500 字硬截断                              | 浅  |
| RAG 检索质量    | 纯向量 topK（`DISTANCE_THRESHOLD = 0.7`），无评测 | 浅  |
| 工程化 · AI 网关 | `RestTemplate` 裸调，无超时/限流/观测              | 浅  |

**结论：产品骨架完成度不错，AI 内核停在"问答"这一代。缺的全是"加模块"，不是"推倒重来"。**

## 2. 技术选型：Java 还是 Python

> **结论：Java 做主线，Python 只留一个对照 demo。**

### 2.1 框架内部选型

**主框架：LangChain4j**

- 不锁 Spring Boot 版本（当前 Boot 3.3.5 可以不动，先跑起来；Spring AI 2.0 强制 Boot 4，会平白多一堆变量）。
- RAG 全链路、Tool、MCP、向量库适配最全，中文实战资料多。
- `@AiService` 抽象层次**低一档** —— 逼你自己实现循环、记忆、压缩，而这些正是面试弹药。

**Spring AI 的用法：只借 MCP 那一段**

MCP Java SDK 出自 Spring 团队，`spring-ai-starter-mcp-server-*` / `-client-*` 是最顺的实现路径。

## 3. 目标架构

### 3.1 最终形态

```
                     ┌──────────────────────────────────────────────┐
   前端 Vue3  ──SSE──▶│  Spring Boot 单进程（JVM 内闭环）             │
   （纯文本对话）      │                                              │
                     │  Controller ──▶ Service ──▶ Agent 内核        │
                     │                              ├─ RAG 检索链路   │
                     │                              ├─ 工具调用(@Tool)│
                     │                              ├─ ReAct 循环    │
                     │                              ├─ 三层记忆      │
                     │                              └─ AI 网关       │
                     └───────┬──────────┬───────────┬───────────────┘
                             │          │           │
                        PostgreSQL   Redis      LLM API（主/备多模型）
                        (pgvector)  (缓存/记忆)
```

**Python 侧：从主链路移除。** 另起一个独立仓库 / 目录放 LangGraph 对照 demo，不参与线上路径，只用于面试对比。

### 3.2 模块划分（7 个）

| 模块              | 职责                                   |
| --------------- | ------------------------------------ |
| **M1 Agent 内核** | ReAct 循环、执行上下文、终止条件、工具调度             |
| **M2 工具层**      | `@Tool` 业务工具 + MCP Server/Client     |
| **M3 RAG 链路**   | 摄取（加载/清洗/切分）→ 混合检索 → 重排 → 上下文拼装 → 评测 |
| **M4 记忆体系**     | 短期滑窗 / 中期摘要 / 长期向量记忆 + 上下文压缩         |
| **M5 AI 网关**    | 多模型路由、语义缓存、限流、重试降级、token 计量          |
| **M6 业务服务**     | 会话、知识库文档、游客画像、统计报表                   |
| **M7 可观测**      | Micrometer 指标、链路追踪、压测数据              |

**设计要点**

- 包的依赖方向单向：`controller → service → agent → rag/memory/gateway → common`，`rag/memory/gateway` 之间不互相依赖。

| **验收** | 一条指令跑完一个多步任务（例：「查一下景区今天天气，判断适不适合户外，再给一条含时段的路线建议」），全程 ≥ 2 次工具调用并自动收敛；**人为注入一个必失败的工具，Agent 能自纠或优雅告知而不崩** |

| 交付物    | **延迟 / 成本对比数据 + 监控面板**                                                                                                |
| **验收** | ① 跨会话能召回用户偏好（如「我对历史感兴趣」）；② ≥ 20 轮长会话不超上下文窗口且 token 增长收敛；③ 产出有 / 无记忆、有 / 无语义缓存的 token 与答对率对比；④ 压测给出 QPS、P99、成功率、单次调用成本 |

4. **不要只做一个玩具 RAG 就收工**：P4 的对比数据和 P8 的压测/监控数据才是区分度。
5. **框架 API 会变，检索质量、编排思想、工程化能力不会变**，把时间投在不变的部分。
